# 스마트홈 공통 기능 조사 및 기초 개발 범위

- 작성일: 2026-10-14
- 조사 목적: 앞선 불만 조사에서 도출한 수요를 기존 스마트홈 앱 기능과 결합해 공통 기능을 확정하고, 초기 개발 범위를 정한다.
- 조사 기준일: 2026-10-14에 확인한 App Store 및 Google Play 공개 페이지

## 1. 조사 요약

10개 앱의 스토어 소개를 비교한 결과, 기기 원격 제어는 10개 앱 모두에서 확인됐다. 자동화·예약은 7개, 음성 제어는 6개, 상태·센서 모니터링은 5개, 공간·그룹·장면 구성은 5개에서 공개적으로 확인됐다. 이 수치는 앱의 전체 기능을 완전히 역설계한 결과가 아니라, 공개 스토어 소개에서 확인할 수 있는 기능 수다.

앞선 불만 탐색에서 드러난 핵심 요구는 연결이 끊겨도 기본 제어가 가능한 것, 기기 실제 상태와 앱 표시가 일치하는 것, 연결 문제를 쉽게 복구하는 것, 지원 범위를 투명하게 알리는 것, 자동화가 실행된 이유와 실패 이유를 확인하는 것이다. 이 요구는 여러 앱에서 흔히 제공하는 제어·자동화 기능 위에 신뢰성 기반 기능으로 얹는 편이 적절하다. 앞선 표본은 탐색 표본이므로 이 수요를 전체 사용자 비율로 해석하지 않는다.

아래 빈도는 “해당 앱에 기능이 없다”는 뜻이 아니라, 스토어 소개에서 해당 기능을 명시적으로 확인한 앱 수다.

## 4. 앞선 불만 조사와 결합한 공통 수요

### A. 연결 상태와 실제 기기 상태를 분리해 보여주기

화면에 “꺼짐”이라고 표시되는 것과 기기가 실제로 꺼진 것은 다를 수 있다. 기기별 마지막 확인 시각, 연결 상태, 앱에서 보낸 명령 결과를 따로 표시한다. 오래된 상태는 최신 값처럼 표시하지 않고 “마지막 확인: n분 전”과 같이 알린다. => 이건 구현방법상 IoT 기기 파악 방식에 따른 한계임. 마지막 확인을 실시간으로 하게 된다면 IoT 기기의 전력 소모가 클것이다. 전력소모 최적화를 위해 어쩔수 없다. 고로 합당한 기능이다. 이 기능은 상태를 2개로 보여지도록 분리하여 보여주도록 설계하여 기능화한다.

### B. 가능한 경우 집 안에서 먼저 제어하기

인터넷 연결이 끊겨도 집 안 네트워크에서 작동 가능한 기기와 기능은 로컬 제어를 유지한다. 원격 연결이 필요한 기기는 원격 불가 상태와 원인을 분명히 보여준다. 초기 출시에서는 모든 장치의 오프라인 지원을 약속하지 않고, 연결 방식별 지원 범위를 등록 단계에서 안내한다.

### C. 연동 가능 범위와 기기 기능을 투명하게 공개하기

기기 모델별로 지원하는 기능(켜기/끄기, 밝기, 온도, 센서값, 자동화 트리거)을 표시한다. 발견만 되고 실제 제어가 안 되는 기기를 “연동 완료”로 표시하지 않는다. 제조사·표준별 제약과 필요한 허브도 추가 전에 안내한다. => 하지만 소비자가 납득될만한 이유를 띄워야 한다. 최대한 직관적이여야 하며, 실제로 사용 및 테스트 해보면서 사람들이 어떻게 하면 잘 알아듣고 투명하게 공개할지 설계단계에서 고심 해야한다. 또한, 지원기능은 명확하게 표시해야한다.
ex) IoT 기기에 직접 연결시, "현재 연동 기기는 00기기를 지원합니다. 이 기기를 지원하는 허브는 xx허브입니다. 이 기기는 스마트폰으로 직접 조종이 가능하지만, 전력 최적화를 위해 허브를 구입하시는것을 추천드립니다." 이런식으로 배포하기
이때 챗봇을 도입하여 연결이 안되는 이유와 무슨 허브를 구입해야하는지, 사용자에게 설명해줘야 한다(나중에 추가할 기능)

### D. 자동화가 왜 실행됐는지 추적 가능하게 하기

각 자동화의 조건 충족, 실행된 동작, 결과와 실패 이유를 시간순으로 남긴다. 사용자가 수동으로 기기를 조작하면 자동화와 충돌하지 않도록 일시 정지·다음 예약 건너뛰기·자동화 재개를 선택할 수 있게 한다. => 확실히 좋은듯, 알림형태로 사용자에게 인지하도록 하고, 행위 충돌 방지 기능으로 도입

### E. 연결 복구와 재설정을 안전하게 만들기

기기 오프라인, 인증 만료, 허브 연결 끊김을 구분해 안내하고, 재시도·재인증·재검색 절차를 제공한다. 가능한 설정은 백업·복원해 재설치나 공유기 교체 후 자동화와 방 구성을 다시 만들지 않게 한다. => 백업 및 복원 기능으로 도입

### F. 공유와 개인정보 권한을 최소 단위로 설정하기

가족 사용자를 초대하고 제어 권한을 역할별로 구분한다. 문 잠금·보안 해제·가스 등 민감 동작은 별도 인증 또는 제한 권한을 적용한다. 카메라·마이크·위치 권한은 기능별로 설명하고 필요한 때만 요청한다. => RBAC 기반 설계를 적용하여 권한을 인가/양도/회수 가능하도록 한다.

## 5. 기능 확정 및 기초 개발 범위

### 1차 개발(MVP)에 포함

1. **집·방·기기 기본 구조**: 집 생성, 방 지정, 기기 등록·이름 변경·그룹 묶기.
2. **기기 제어와 상태 신뢰 표시**: 가능한 기능 제어, 현재 상태, 연결 여부, 마지막 확인 시각, 명령 접수·완료·실패 상태를 분리해 표시.
3. **기능별 호환성 안내**: 기기·모델마다 가능한 제어와 자동화 기능을 등록 전에 공개.
4. **간단한 자동화와 장면**: 시간 또는 지원되는 기기 상태를 조건으로 한 동작, 여러 기기 그룹 동작, 자동화 켜기·끄기.
5. **자동화 실행 기록**: 실행 시각, 조건, 기기별 명령 결과, 실패 원인, 재시도 안내.
6. **오프라인·오류 복구 흐름**: 로컬 제어가 가능한 경우 우선 시도하고, 연결 문제별 설명과 복구 단계 제공.
7. **설정 백업·복원**: 방·기기 이름·그룹·자동화 설정을 계정에 저장하고 복원.
8. **수동 조작 우선권**: 사용자가 직접 조작했을 때 해당 자동화를 잠시 보류하거나 재개하는 선택지 제공.
9. **기본 사용자 권한**: 소유자와 일반 가족 구성원의 권한 분리 및 초대 취소.

### 후속 단계(P1)

- 여러 제조사·프로토콜을 아우르는 추가 연동 어댑터
- 카메라 라이브 영상과 이벤트 검색, 에너지 분석, 음성 제어, 위젯
- 고급 조건(일출·일몰, 위치, 복합 센서 조건), 자동화 템플릿
- 센서 배터리·허브·네트워크 상태 진단, 장기 이력과 기기 건강 요약
- 가족 역할 세분화와 민감 기기 동작에 대한 추가 확인 절차

### 초기 범위에서 제한할 항목

- 확인되지 않은 모든 브랜드·기기와의 호환을 약속하지 않는다. 먼저 실제 보유 기기와 연결 경로를 정해 그 조합의 등록·제어·상태 확인을 완성한다.
- 카메라 분석, 음성 인식, 에너지 최적화 추천은 초기 필수 기능에서 제외한다.
- 가스·출입문 잠금 등 안전 영향이 큰 동작은 상태 확인과 권한·인증 정책이 검토된 기기부터 제공한다.

이 기준은 구현 후 검증할 제품 요구사항이며, 본 조사는 해당 동작을 테스트한 결과가 아니다.

- 명령을 보낸 후 기기가 실제로 응답하지 않으면 “성공”으로 표시하지 않고 실패 또는 확인 불가로 구분한다.
- 상태값에는 마지막 확인 시각을 붙이고, 일정 시간 이상 갱신되지 않은 값은 오래된 상태로 표시한다.
- 자동화 기록에서 조건이 충족됐는지, 각 동작이 실행됐는지, 실패했다면 무엇이 막았는지 확인할 수 있다.
- 인터넷이 끊겼을 때 로컬에서 지원하는 기능은 동작하고, 원격 서비스가 필요한 기능에는 제한 사유를 표시한다.
- 기기 재연결이나 계정 복원 후 방·그룹·자동화 설정이 유지된다.
- 지원되지 않는 기기 기능은 설정 화면에서 미리 알리고, 작동할 것처럼 보이는 실행 버튼을 노출하지 않는다.

## 7. 결론

초기 스마트홈 베이스는 **기기·방 통합 제어, 신뢰할 수 있는 상태 확인, 기본 자동화, 자동화 기록, 연결 복구, 기기별 호환성 공개, 설정 복원, 수동 조작 우선권**을 공통 기능으로 확정하는 것이 적절하다. 원격 제어·자동화·음성 같은 이미 익숙한 기능을 바탕으로 하되, 사용자가 “명령이 정말 실행됐는지”, “왜 안 됐는지”, “어떻게 복구할지”를 알 수 있게 하는 것을 MVP의 핵심 품질로 둔다.

음성 제어·카메라·에너지 분석·다수 프로토콜 연동은 후속 단계로 둔다. 단, 실제 초기 기기군이 정해지면 그중 어떤 연동 어댑터가 첫 MVP에 필요한지 구체화해야 한다.
